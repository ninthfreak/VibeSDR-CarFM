## TIER 1 — The driver loses the radio, and it never comes back

### 1. Audio focus loss kills sound and the face lies about it (two defects, both live)
**`src/screens/RadioScreen.tsx:913`, `:1985`, `android/.../VibeStreamService.kt:254-275`** — high

Two findings merged here; they are the same event (`AUDIOFOCUS_LOSS`) producing opposite wrong outcomes on the two backends, and they must be fixed together because each path's fix is the other's missing half.

- **NWD path:** `-1` or `-2` sets `fmAudioActive=false`, which drives `off` in `CarFmFace.tsx:527` — full-screen grayscale, signal forced to `--`, stereo pill blank, all tells dropped, genre hidden, hero veiled, hero-swap animation disabled. Recovery requires change `1` (GAIN). Android does not deliver GAIN after a permanent LOSS, and the only `requestAudioFocus` in the session is `startNwdControlSession`, called once at connect. Android Auto plays music, the MCU hands the source back to FM, audio returns — the face stays grey for the rest of the drive. Separately, `-2` (LOSS_TRANSIENT, what a nav prompt raises) grayscales the entire radio for the duration of a spoken direction.
- **SDR path:** the inverse. `emitEvent("VibeFocus")` exists only inside the `if (nwdControl)` early return, so on a dongle/remote session `AUDIOFOCUS_LOSS` runs `stopEngine(); stopSelf()` and emits nothing. `fmAudioActive` stays at its initial `true`, `fmTunerError` is driven only by the spectrum WS, `AudioPlayer.tsx` has no watchdog. The face stays fully lit with a frozen signal bar and live-looking RDS while producing no sound; play/mute are no-ops because the service instance is gone.

Fix: emit `VibeFocus` from the non-`nwdControl` LOSS branch and from `stopEngine`; on `-1` re-request focus (or poll `mcu_current_source`) so a recovery path exists; treat `-2` as a dim, not a stop.

### 2. Night start renders a full-white face, all night
**`src/screens/RadioScreen.tsx:2118`** — medium

Two findings merged — same variable, same root cause, two triggers. `fmIllNight` has exactly one writer: the change-only `NwdIllState` broadcast. `startIllWatch` registers for `com.nwd.ACTION_ILL_STATE_CHANGE` with no initial read, and `currentStateMap` carries no illumination field, so `connect()` cannot seed it. This ROM keeps `androidUiMode` at DAY permanently (measured, comment at `:2114-2117`), so `theme='system'` + `fmIllNight=null` resolves through `useColorScheme()` to the full-brightness LIGHT palette.

- Ignition on after dark with headlights already lit → the broadcast fired before registration (or never repeats) → white face in the driver's eyeline until the headlights are physically cycled.
- `startIllWatch` is only reachable from `connect()`, which is gated on `route.params.tunerless` — so an RTL-SDR session never registers the receiver at all and is white all night regardless.

### 3. Genre disappears and stays gone — the poll overwrites the decoder
**`src/screens/RadioScreen.tsx:2491`** — high

The 1.5 s AIDL poll merges `pty: (typeof p.pty === 'number' && p.pty >= 0) ? p.pty : prev.pty`. `p.pty` is `getPTYType().toInt()`, guarded only against a throw; on a unit that never decodes RDS this byte getter returns `0`, and `0 >= 0` passes. `ptyLabels.ts:27-30` returns `''` for `pty <= 0`, so the genre line vanishes. It does not self-heal: `push()` only returns non-null when the decoder's *internal* state changes, and internally `st.pty` is still 22 — so no later group re-applies it. Only an unrelated RT/PS change restores it. On a station with changing RadioText the genre blinks between correct and absent.

Refuted sub-claim: the poll cannot blank RadioText (`text: p.rt || prev.text`).

### 4. RDS never expires — the plate scrolls a dead station's song over static
**`src/screens/RadioScreen.tsx:2510`** — medium

`liveStation` has three NWD writers; only the `NwdRadioFrequency` handler clears anything, and every merge is `x || prev.x`. No timestamp, no timer anywhere in the file. Drive out of range without touching the dial: groups stop passing consensus (silence, not a clear), so the RadioText plate keeps scrolling the last song, the genre keeps the old PTY, TP/TA stay latched, and `rdsOk` stays lit indefinitely over hiss.

Overstated in the original: hero name and logo would persist anyway via the FCC frequency fallback — that is by design.

### 5. PI is lost permanently once the decoder is reset onto the same station
**`src/services/nwdRds.ts:95`, `:144`, `src/screens/RadioScreen.tsx:2439`** — high

**Three findings merged** — this was reported three times from three angles (decoder-internal, decoder-external, screen-caller). One defect: `reset()` rebuilds `st` from `BLANK` (`pi: null`) but deliberately leaves `piConfirmed` set, justified by a comment saying "the caller sets it immediately after." No caller can — the exported interface is exactly `{ push, reset, state }`, no setter. Every subsequent group carrying that same PI hits the `a === piConfirmed` branch, which only zeroes `piPendingCount` and never re-assigns `st.pi`. Reproduced by executing the shipped decoder: prime on WERN (PI `a6ff`) → `pi: 42751`; `reset()`; 800 more identical groups → `pi: null` forever.

`RadioScreen.tsx:2439` calls `reset()` on **every** `NwdRadioFrequency` event, so the trigger is ordinary: re-pressing the active preset, PREV-then-NEXT landing back home, an FM1↔FM2 toggle on the same frequency, the wheel path at `:2475-2478`, or a vendor re-notify once `psName` populates. A normal retune X→Y is fine.

Driver impact, corrected across the three reports: `identifyByPi` → `piIdentity` → `fmCallsignHint` goes dead. On a station with a *scrolling* PS — which this decoder deliberately never publishes (the documented 101.5 "IBA-FM" case) — `name` is also empty, so `rdsOk` (`!!liveStation.pi || !!liveStation.name`) is false: **the RDS tell sits dark while RadioText scrolls on the plate right below it.** Two consequences claimed in the reports do *not* exist: `resolveStationLogo` returns `null` unconditionally (`AUTO_LOGO_RESOLUTION` off), and the AF follow is inert (`afMhz` only ever comes from SDR metadata; this decoder does not decode AF).

Fix, reconciled: re-assert in the `else` branch (`if (st.pi === null) st.pi = piConfirmed`) **rather than** clearing `piConfirmed` in `reset()` — clearing drops the decoder into the no-incumbent path where any 3-group corrupt run is adopted outright.

### 6. A single cold-start miss kills RadioText for the whole session
**`android/.../NwdRadioModule.kt:237`** — medium

`startRdsPump()` is called synchronously inside the `bindService` success branch, so it runs its one-shot `getRadioRDSDataArm()?.length == 16` support gate before `radio` exists, before `setRDSState`, and before JS claims the FM source. Exactly one call site; `connect()` short-circuits once bound; nothing re-arms it. Launch CarFM while the head unit is on Bluetooth → gate reads a dead front end → `supported=false` → no `NwdRdsGroup` event ever, so PI, PS and RadioText are empty until the app is force-killed. RadioText on this unit comes only from this pump (`getRtMessage()` is empty on the Allwinner manager).

Downgraded from high: the reviewer's cited evidence (findings doc `:839`) is misattributed to a removed RSSI sweep. What survives is that the gate has never been evaluated under the conditions it actually runs in.

### 7. An AM reading at connect permanently breaks the dial
**`android/.../NwdRadioModule.kt:306`** — medium

`freqMult` is calibrated once from whatever the tuner happens to be on at connect, accepting any reading including a non-FM band, and is never re-derived. The team already caught this exact staleness class for `fmBand` and fixed it by re-assigning on every `notifyCurrentFrequency` (`:757-773`) — while leaving `freqMult` frozen two lines above, where `putDouble("mhz", freq/freqMult)` consumes it. Head unit last on AM: `freq=1000` → `1000 > 500` → `freqMult=10`. The FM claim repairs `fmBand` but not the scale, so the face reads "1059.0" MHz and `tune(102.5)` sends `1025` — outside the `8750..10790` plan. The dial spins and the radio does not move, for the rest of the session.

Refuted sub-claim: the `fv==0 → freqMult=1` branch has no device evidence; the cited doc §10 is about the vendor *static*, not the AIDL getter.

### 8. A vendor service that binds but never connects leaves an inert face
**`android/.../NwdRadioModule.kt:83`** — low

`connectPromise` is settled only inside `onServiceConnected`; `disconnect()` never touches it; there is no timeout and no rejection path. Everything that clears `fmTunerError` — `setNwdActive`, `nwdSetAudio`, all six `onNwd` subscriptions, the 1.5 s poll — lives after `await nwdConnect()`. If `com.nwd.radio.service` crashes in `onCreate` or returns a null binder, PackageManager still resolves it and `bindService` returns true, so the driver sits on the tuner-error pill with an inert seek control and a frozen readout, with no path back short of killing the app.

Downgraded on reachability only (`isAvailable()` pre-resolves the service; bind failures are handled). The "second `connect()` overwrites the first" sub-claim is unreachable — single call site with cleanup-ordered `disconnect`.

## TIER 2 — The driver reads the wrong thing on the biggest text on screen

### 9. `cleanCall()` amputates real station identities and deletes every space
**`src/components/carfm/tokens.ts:94`** — high

`.replace(/[\s-]*(fm|am)\b/ig,'').replace(/[-\s]+/g,'')`. Run in node: `"WHAM"→"WH"`, `"KJFM"→"KJ"`, `"KAFM"→"KA"`, `"TEAM 1300"→"TE1300"`, `"SLAM FM"→"SL"`. Call sites are all live: `CarFmFace.tsx:784` (PS or hint), `:797` (FCC callsign base — so real calls like KJFM/KAFM are hit), `NearbyPicker.tsx:85`, `LogoTile.tsx:343` for every preset plate. `heroIdent` renders at 94dp on the wide track.

The second consequence, found during verification and not in the original report, is worse: the unconditional space strip runs on `callsignHint`, which `RadioScreen.tsx:2024` builds as `` `${callsign} · ${city}` `` — so the hero identity becomes **"WKSC·Chicago"**, all spaces gone, at 94dp with `numberOfLines=1`, clipped.

### 10. RadioText silently loses its tail on the tall track
**`src/components/CarFmFace.tsx:279`** — medium

`marquee = shown.length > 46` with no reference to measured width. On a 341dp vertical-third slice the content width is 263dp at 21pt ≈ 25 characters, so anything in the 25–46 band never scrolls. Corrected failure mode: with `numberOfLines=1` and `ellipsizeMode="clip"`, RN Android builds a `StaticLayout` with a null ellipsizer that wraps at a word boundary and draws only the first line. `"Now Playing: Rolling Stones - Angie"` shows as `"Now Playing: Rolling"`, centred, motionless, no ellipsis — and the song title is never visible. Wide and landscape tracks fit ~55–60 chars, so 46 is only wrong on `tall`.

### 11. A truncated RadioText fragment lands on the plate after every retune
**`src/services/nwdRds.ts:227`** — medium

Line 217 latches `rtEnd` on any `0x0D`; line 227 publishes on `rtEnd !== null` alone and never consults `rtSeen`. Acquisition genuinely lands mid-cycle — PI consensus burns 3 groups before any RT group is admitted. Replayed: segments 2, 3, then a segment-4 group carrying CR → `st.rt === "        tta Love"`. `RadioScreen.tsx:2453` does `s.rt || prev.text` (leading-space string is truthy) and `CarFmFace.tsx:777` trims, so the driver reads **"tta Love"** on the plate for one RT cycle (~2–5 s) after a retune, then it self-corrects.

Corrected: the report's second example (lone terminator, nothing before) yields `""`, which `s.rt || prev.text` treats as falsy — harmless.

### 12. The RadioText marquee jerks 50dp backwards every 16 seconds
**`src/components/CarFmFace.tsx:288`** — medium

`rtTrack` is `{flexDirection:'row', columnGap:100}` with two identical Texts, so the measured `trackW` is `2*copyW + 100`. Line 288 animates to `-trackW/2` = `-(copyW+50)`; a seamless seam needs `-(copyW+100)`. At loop reset the text visibly jumps 50dp left, mid-sentence, on every cycle of any RT over 46 chars. Nothing is lost — the line hitches, repeatedly, in the driver's peripheral vision.

### 13. The palette de-themes up to 2 s before the text it was matched from
**`src/components/CarFmFace.tsx:532`** — low

`resolveEgg({ rt: radioText, ... })` uses the raw prop, while the strip renders the *held* value derived 250 lines later. The hold exists precisely so a themed palette does not flash past (comment at `:774-776`). `NwdRadioFreq` clears `text: undefined` as soon as the vendor moves the dial, while `pending` persists until the device reports the target or the 2 s cap expires. Press NEXT on a themed station: page background, hero card, accent and the RT plate's own colours all revert within a frame while the strip still shows the previous station's text. One-line fix — move the `rt` derivation above line 532.

### 14. A brand-name PS makes the hero drop its logo and re-lay out
**`src/components/CarFmFace.tsx:784`** — medium

`callsign = cleanCall(ps || callsignHint)` feeds `useStationLogo`, and `LogoTile.tsx:109-110` lets the name-derived base beat the frequency lookup. `callsignFrom`'s `\b([KW][A-Z]{2,3})\b` matches "KISS", "WAVE", "KOOL", "WILD". WKSC-FM with a logo: at tune time base=WKSC → 256dp logo hero; 1–2 s later PS "KISS FM" lands → base=KISS → no logo → `useStationDisplay` flips its defaults and the hero becomes big call text **plus a newly-appeared frequency row**. Alternates back on stations sending dynamic PS fragments.

Downgraded to medium: `cleanCall` strips spaces first, so "THE WAVE"→"THEWAVE" and "103-5 KISS"→"1035KISS" no longer match the `\b`-anchored regex. Only a bare 3–4 letter K/W token triggers it.

### 15. A distant station's logo paints over dead air
**`src/components/carfm/LogoTile.tsx:109`** — low

`refreshFreqMap` maps each channel to the closest FM station within 100 km with **no receivability threshold**, and nothing consults `score` even though `estimatedSignalDbForFreq` computes it for the same channel. Tune an empty channel occupied by a 90 km class-A licensee: the hero shows that station's real logo and callsign at full size over hiss, with only the grey zero EST bars dissenting.

### 16. The hero shows a bare frequency when the preset's own name was captured and discarded
**`src/components/CarFmFace.tsx:716`** — low

`pending.name` is written at `:765` and read nowhere. During the hold `ps` is forced `''`, so identity comes solely from `callsignForFreqSync`, which reads the persisted freq→callsign map — empty on a fresh install until a GPS fix builds it. Fresh install, preset "WOLX 94.9" stepped from the wheel: the hero shows only the amber 94.9 while the driver's own saved name sits on the peek card beside it.

### 17. The signal meter freezes at the tune-time estimate
**`src/screens/RadioScreen.tsx:2361`** — low

`scheduleSignalEst` has exactly two call sites — the connect seed and the frequency handler. No interval, no GPS-fix subscription. Tune near the transmitter, drive 50 miles: the grey bars keep the departure-point estimate while the audio is static. Downgraded from high because the meter is deliberately rendered grey/estimated and reads zero with no fix — a secondary cue, not audio truth. Refuted sub-claim: the poll cannot catch a frequency change the callback misses; `notifyCurrentFrequency` is confirmed delivered.

## TIER 3 — Visible glitches, transient or cosmetic

### 18. The departing hero-swap clone mutates into a coloured letter box
**`src/components/CarFmFace.tsx:1442`** — medium

`renderPeek` passes `freqMhz={preset.frequencyMhz}`; the fade clone at `:1442` passes nothing, and `FlipDescriptor` only carries `cloneName`. `PresetPlate` then has `base=null` and renders `CallSignBox` labelled `cleanCall("FM 100.3").slice(0,4)` = **"100."** over `brandColor`, omitting the frequency Text and re-centring the stack. This is the common case, not an edge one: `RadioScreen.tsx:2219` names a preset `` `FM ${mhz}` `` whenever no PS was captured at save time, which is most saves on the NWD tuner. Press NEXT and the outgoing clone of a logo-bearing card fades out as a coloured "100." box over 520 ms.

### 19. Cold start flashes the amber tuner-fault pill over a hardcoded 98.5
**`src/screens/RadioScreen.tsx:2034`** — low

`fmTunerError` initialises true for a tunerless launch and the effect re-asserts it immediately with no grace, while the SDR path gets 6 s. It clears only after `isNwdAvailable()` and `nwdConnect()` resolve. `status.frequency` starts at `98_500_000`. Ignition on: the first frames show "Failure to connect to tuner." over 98.5 MHz, then snap to the real dial. Downgraded from high — both awaits are a PackageManager lookup and a local bind, so this is a few hundred ms flicker, not a persistent fault display.

### 20. Auto-scroll centres the tuned preset on a stale tile width
**`src/components/carfm/PresetsBand.tsx:254`** — low

`activeIndex * (TILE_W + GAP) - (viewW - TILE_W)/2` with `TILE_W=148`, used nowhere else; the real pitch is `S(118) + 10` = 128dp at k=1 (116 in landscape). 30dp of error per index. Worked: `viewW=800`, 12 presets, tap the 7th → scrolls to 622 where centring needs 443, leaving the highlighted tile ~179dp left of centre. Stays on screen for ordinary preset counts; clips off the left edge past index ~12.

### 21. Peek plates flash a letter box because the warm cache warms the wrong sizes
**`src/components/carfm/LogoTile.tsx:65`** — low

`warmStationLogos` warms `${base}|${sz??0}` for `[undefined,128,192]`; `SidePresetCard` computes `plateW = min(round(width*0.92), s(184))` and passes it as `boxDp`, so the key is `|184` on the wide track and `|63` on a third slice — neither warmed. The comment at `:55` claims the sizes match; they don't. Cold start with 12 presets: both flanking peek cards, and each preset the first time it rotates into a peek slot, flash a coloured 4-letter box — landing on top of the 520 ms hero morph. One or two frames; the module cache holds it thereafter.

### 22. The TA indicator latches on under block-B corruption
**`src/services/nwdRds.ts:167`** — low

`st.tp` and `st.ta` are both written only inside `if (ptyCount >= PI_CONFIRM)`, and `ptyCount` resets to 1 whenever the PTY field differs. Replayed: 6 clean groups with TA=1 → `ta === true`; then 400 groups all carrying TA=0 with the PTY field alternating 22/7 → still `true`; 3 clean groups finally drop it. `CarFmFace.tsx:1120` renders TA as a pulsing tell replacing TP, so the driver gets a pulsing traffic-announcement indicator with no announcement in progress. Needs block B corrupting the PTY bits specifically — a TA flip on a stable-PTY station updates immediately.

### 23. PI acquisition has a heavy tail on a noisy station
**`src/services/nwdRds.ts:128`** — low

Both PI branches reset `piPendingCount` to 1 on any differing value, making acquisition a strict run of 3 rather than a majority over a window. Monte-Carlo over the actual code path: p=0.5 → 14 groups (~1.2 s); p=0.7 → 51 (~4.5 s); p=0.9 → 1095 (~96 s). A failed gate `return null`s, so nothing downstream runs, and there is no fallback — `psName`/`getRtMessage` stay empty for a passive bound client, so the 1.5 s poll cannot backfill. Blank name, blank genre, blank RadioText with no indication why.

Two claims did not survive: the "silent forever" demo was an artifact of deterministically alternating PIs (real corruption is not phase-locked, so the run always converges — heavy tail, not dead end), and p=0.9 is unevidenced (the nine distinct block-A values in the comment are a *set* of corrupt values, not a rate). The "PTY gate unreachable while PI is unconfirmed" sub-claim is true but is the gate doing its job.

### 24. The STEREO pill can be driven by the untrustworthy signal
**`android/.../NwdRadioModule.kt:776`** — low

`notifyStereo` (transaction 4) and `notifyStereoOn` (transaction 5) both emit `NwdRadioStereo {on}`, but the docs list `isHasStrero()` and `isStreroOn()` as different reads, and record `isStreroOn()` stuck true on dead air — which is why the connect-time seed was removed while the push twin stayed wired. `setStereoDebounced` is last-write-wins over 2 s, so on a fringe mono station a `notifyStereoOn(true)` arriving within the window lights the STEREO pill and holds it until the next `notifyStereo`. Downgraded: no device evidence `notifyStereoOn` ever fires, and these callbacks fire only on change.

## TIER 4 — Fabricated diagnostics and mislabelled controls

### 25. The tuner Details panel prints hardcoded identity as live measurement
**`src/components/carfm/SettingsPanel.tsx:264`** — medium

A literal array `[['Device','Realtek RTL2832U + R820T2'],['USB ID','0bda:2838'],['Sample rate','2.048 MS/s']]` is mapped into a diagnostics table. None is read from anything — the session's real rate is `hwSampleRate`, default 2.4 MS/s and user-settable. Separately `detected: nwdActive ? false : !tunerError`, and `tunerError` means "no live tuner session" — so a connected remote OWRX/UberSDR/Kiwi clears it with no dongle present. Connect to a remote server over the network and Settings reads "Connected · Local hardware · RTL-SDR (RTL2832U)", "Detected", "Sample rate 2.048 MS/s". `NwdRadioModule.kt:440-442` describes its own getters as "the honest replacement for the representative strings in the settings diagnostics"; the replacement never happened.

### 26. The appearance control is labelled as the opposite of what it does
**`src/components/carfm/SettingsPanel.tsx:320`** — low

The row reads "Overrides the system colour scheme on the radio" with chips SYSTEM / LIGHT / DARK. But the ROM's scheme is permanently DAY, and `fmThemeEffective` consults `fmIllNight` *only* under `system` — so SYSTEM is in fact "follow the headlights" and LIGHT/DARK silently disable automatic dimming. A driver who picks LIGHT once to escape the white-at-night cold start (finding #2) permanently disables headlight dimming, and nothing in the panel says so. Wording-only fix, but it is the one setting that controls night readability.

### 27. `setRDSState(0, ...)` is documented as verified and is a no-op
**`android/.../NwdRadioModule.kt:315`** — low

`r.setRDSState(0.toByte(), true)` carries the comment "same guess the spike confirmed works", while this repo's own docs state in three places that the call only acts on `which==1` (AF) and `which==2` (TA) and "calling it with which = 0 sets nothing." `setRdsEnabled` uses selector 0 too. No runtime consequence — RDS comes from the raw-group pump and the call is in a swallowing try/catch — the harm is that it fabricates verification for an inert call.

## TIER 5 — Waste and maintainer traps (no driver-visible symptom)

### 28. The RDS pump never pauses and re-resolves reflection at 11 Hz
**`android/.../NwdRadioModule.kt:524`** — low. `nwdFmGet` does `Class.forName` + `getMethod` on every 90 ms iteration; `stopRdsPump()` has one caller (`disconnect`), and `setAudioEnabled(false)` does not touch it. Press power off and the thread polls a released tuner for the life of the app. Mains-powered head unit, so this is waste, not drain.

### 29. Nothing pauses on background
**`src/screens/RadioScreen.tsx:1303`** — low. The AppState handler returns immediately for tunerless; neither the pump nor the 1.5 s poll is gated, and the foreground media notification keeps the process unfrozen. An hour backgrounded with the screen off keeps both loops running into a decoder whose output nothing renders.

### 30. `probeNwdFmManager` blocks its dispatch queue for ~960 ms
**`android/.../NwdRadioModule.kt:638`** — low. 8 × 120 ms `Thread.sleep` inside a `@ReactMethod`, plus a 53-entry method dump and nine reflective calls, before `promise.resolve`. Every other `NwdRadio` call serialises behind it. Note `newArchEnabled=true` with a plain `ReactContextBaseJavaModule` via interop — the blocked queue is arch-dependent and could be the JS thread. Reaching it needs a deliberate tap on the diagnostics probe button; the claimed equivalence to the auto-fired `probe()` is wrong (`probe()` has no sleeps).

### 31. Seven write-only `useState` hooks, one funding a whole dead subsystem
**`src/screens/RadioScreen.tsx:1585`** — low. `serverLost`, `reinit`, `owrxDspDefaults`, `dabSpeed`, `vtsNotif`, `vtsMenuName`, `vtsMenuFreq` each appear exactly once outside comments — their declaration — against 2/6/1/1/4/3/4 setter calls. `liveLogo` is read at exactly one place: inside the effect that builds the discarded `vtsNotif`, and the logo effect calls `resolveStationLogo` purely to populate it. The `vtsNotif` dep list includes `liveStation.text`, so every decoded RadioText change forces a re-render of the 2,728-line screen and the SVG-heavy face for a value nothing renders.

### 32. Four dead paths left by today's removals
**`src/services/SDRBackend.ts:255`** — low. `onReceiverLon` is declared and fired from three adapters with no implementation receiving it. `nwdSendPanelKey` is exported with zero other matches, leaving `NwdRadioModule.sendPanelKey` unreachable. `rtCandidate` is assigned four times in `nwdRds.ts` and read nowhere, and its comment documents a two-cycle publish rule the decoder explicitly dropped. `tunerCapabilities.ts` has no importer anywhere.

### 33. `tunerCapabilities.ts` contradicts itself and miscounts its own targets
**`src/services/tunerCapabilities.ts:51`** — low. Three of four claimed falsehoods hold: the doc-comment says NWD RadioText is "unsupported on current evidence" ten lines above a profile marking it `'live'` as of 2026-08-01; the header's "59/21/10 branch sites" measures 12/7/6; the MIGRATES pointer names `CarFmFace.tsx:1070-1072` where the branch is at 1076/1078. **Refuted:** the `stationIdentity: 'frequency-db'` note is accurate — the PI path added today is an additional source, not a replacement. Nothing imports this module, so no behaviour depends on any of it.

### 34. Three `RadioScreen.tsx` comments state the opposite of the code beneath them
**`src/screens/RadioScreen.tsx:1987`** — low. `:1987` says the NWD meter is driven by the tuner's own signal level via `arg` — the same file at `:2431-2434` and the native module both record `arg` as the preset-slot index, and the meter is fed by `scheduleSignalEst`. `:2125-2127` says audio claim/release is "visual state for now, native deferred to task #14" while `:2136`/`:2143` already call `nwdSetAudio`, and it names "ExitFm", the mechanism the native module records as disproven. `:910-912` still labels the `VibeFocus` listener "DIAGNOSTIC" though it now blanks the entire face. The `:1987` comment specifically re-opens the RSSI hunt that took four sessions to close.

### 35. Three native comment defects, one actively dangerous
**`android/.../NwdRadioModule.kt:228`** — low. ## COMPLETENESS CRITIC — what this audit did not cover

This audit is not a clean bill of health for anything it did not open. Specifically:

**Never opened at all.** `AudioPlayer.tsx` was read only far enough to confirm it has no watchdog and no retry — its buffering, underrun handling, and behaviour on a WebSocket drop are unexamined. `stationFinder.ts` was read for `refreshFreqMap`, `callsignForFreq*` and `estimatedSignalDbForFreq`; its GPS acquisition, permission handling, cache persistence and refresh cadence were not. `OwrxAdapter.ts`, `UberSDRAdapter.ts` and `KiwiAdapter.ts` were grepped for one dead callback and nothing else — the entire remote-SDR protocol layer (reconnect, auth, sample-rate negotiation, error surfacing) is unaudited. `web/client/src/main.ts` was touched only for a stale comment. `bandThemes.ts` and `NearbyPicker.tsx` were each read at a single call site.

**Whole behaviours with no finding, because they were not exercised.** Preset add/delete/reorder and its persistence. AsyncStorage/MMKV schema migration — nothing here checked what happens to a stored preset list or settings blob written by the pre-rename build. Orientation change and the landscape/tall track transitions at runtime (only their static geometry was computed). Seek and scan behaviour end to end, including what happens when a hardware seek races a JS `tune()`. The band switch (FM1/FM2/AM) beyond the `freqMult` interaction. Bluetooth/phone-call interruption other than through the audio-focus path. Process death and restore.

**Native surface examined narrowly.** `NwdRadioModule.kt` was read closely, but `VibeStreamService.kt` was only inspected around focus handling and `startNwdControlSession` — its notification lifecycle, `stopEngine` teardown ordering, and USB permission flow are unchecked. `VibeStreamModule.kt` got one grep hit. There is no AIDL-level review of `RadioCallback` transaction ordering or of what happens when the vendor service dies (`onServiceDisconnected` was noted as leaving the pump running; nothing else about that path was traced).

**Concurrency and lifecycle, largely untested.** Effect cleanup ordering across the connect/disconnect cycle was asserted at one point (finding #8's refuted sub-claim) but not systematically checked. React 18 StrictMode double-invocation, rapid mount/unmount from fast navigation, and whether the six `onNwd` subscriptions can leak on a re-run of the connect effect are all open. The decoder's behaviour under interleaved `push()` and `reset()` from different event sources was only exercised in the specific replays above.

**Verification method has a ceiling.** Every decoder finding was reproduced by executing the shipped code against synthetic or captured groups. Nothing in this audit ran on the device. Findings #6 (`startRdsPump` gate), #7 (`freqMult` from an AM reading), #8 (bind-without-connect) and #24 (`notifyStereoOn`) all describe conditions that have never been observed on hardware — they are sound readings of the code whose *trigger probability* is unknown. Conversely, two findings were downgraded specifically because their cited device evidence turned out to be misattributed; the same could be true of evidence I accepted.

**Not assessed as a dimension.** Accessibility and touch-target sizing for in-motion use. Startup time and time-to-first-frame. Memory growth over a long drive. Any form of error reporting or crash telemetry. Whether the 41 findings interact — e.g. #2 (white night face) pushes the driver toward the LIGHT setting, which #26 shows silently disables the dimming that #2 is about; that class of compounding was not searched for systematically.
